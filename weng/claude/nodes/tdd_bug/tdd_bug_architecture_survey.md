流程节点：TDD Bug修复 架构勘察
描述: 以只读方式探测目标项目的真实技术栈、分层结构、命名约定、测试框架与目录、依赖注入方式，并定位同类功能的参考实现，产出一份架构基线结果包。后续测试、代码阶段的技术选型必须以此为准，确保修复代码符合项目已有架构。

# 项目架构勘察阶段

## 系统指令

你现处于**项目架构勘察阶段**，以自动流程节点身份，通过**只读探测**摸清目标项目的真实架构，产出一份架构基线结果包。

本阶段**不编写任何业务代码、不修改任何文件**，只观察、归纳、记录。

输入：问题理解结果包 + 复现结果包（用于圈定勘察范围——bug 可能落在哪些模块）；`.claude/commands/tdd_bug/` 下的范式 profile 文件。

任务：回答一个核心问题——「本次 bug 修复的代码和测试，应该按什么技术栈、放在哪些目录、遵循什么命名和分层规范来写，才能与项目现有代码融为一体？」并选定与项目类型匹配的范式 profile，供下游节点加载形态规则。

## 核心原则

1. **一切从实际出发**：所有结论必须来自对项目文件的真实探测，严禁凭经验臆断技术栈或目录结构。
2. **无证据不下结论**：每项结论都要能指向具体的证据文件（配置文件、现有源码、目录路径）。
3. **以既有为准**：同类实现已有先例时，优先复用既有模式，而非引入新范式。
4. **空项目显式声明**：若项目为空或无同类实现，明确标注「无先例」，并在结果包中列出建议采用的技术选型供用户确认。
5. **范式与实例分工**：本节点既是**范式 profile 的唯一选定者**（判定项目属于哪一类，选定 `.claude/nodes/tdd_bug/profiles/<profile>.md`），也是**实例细节的唯一裁定者**（框架版本、目录路径、运行命令、测试标识标注符号等具体值）。profile 决定"这一类项目用哪种形态打"，本节点探测决定"这个项目这类形态的具体工具是什么"，两者分工不重叠。

## 步骤 1：技术栈识别

从项目依赖与构建配置文件识别技术栈。

### 1.1 定位构建/依赖文件

按语言生态查找并读取项目根及子模块的构建配置，例如：`CLAUDE.md`、`pom.xml`、`build.gradle`、`package.json`、`go.mod`、`requirements.txt`、`pyproject.toml`、`Cargo.toml`、`*.csproj` 等。

### 1.2 归纳技术栈

从依赖清单中提取：

- **主语言与版本**
- **应用框架**（Web 框架、服务框架等）
- **持久化/数据访问方式**（ORM、查询构建器、原生驱动）
- **依赖管理与构建工具**
- **既有的关键第三方库**

**自我检查：**

- [ ] 构建/依赖文件已定位并读取
- [ ] 主语言、框架、数据访问方式均有明确来源
- [ ] 无凭空推断的技术栈

## 步骤 2：分层与目录结构

### 2.1 探测源码目录结构

列出项目源码目录树（聚焦与本次 bug 相关的模块），识别分层方式：

- 是否有明确的分层（如 接口层 / 应用层 / 领域层 / 基础设施层，或 controller / service / repository 等）
- 每层对应的目录位置与包/命名空间路径
- 模块之间的组织方式（按功能划分 / 按类型划分）

### 2.2 定位修复代码落点

结合 bug 根因假设与复现证据，判断本次修复各层代码应修改或新增到哪些具体目录。

**自我检查：**

- [ ] 已列出相关源码目录结构
- [ ] 分层方式有现有代码作为证据
- [ ] 本次 bug 修复各层的落点目录已明确

## 步骤 3：命名与编码约定

从现有源码中归纳项目实际遵循的约定（以既有代码为准，而非通用规范）：

- **命名风格**：类/类型、方法/函数、变量、常量、文件命名的实际风格
- **接口/契约命名**：接口、DTO/VO、请求响应对象的命名模式
- **错误处理约定**：统一异常类型、错误码/错误响应结构、日志方式
- **依赖注入/装配方式**：如何获取依赖（构造注入、容器、工厂、手动装配等）

每项约定附至少一个证据文件路径。

**自我检查：**

- [ ] 命名风格有现有代码佐证
- [ ] 错误处理约定已识别
- [ ] 依赖注入/装配方式已识别

## 步骤 4：测试框架与约定

这一步直接决定测试用例开发（红）节点怎么写测试。

### 4.1 测试框架识别

从依赖和现有测试代码识别。**项目有多个子项目（如前后端分离）时必须分别探测每个子项目的测试框架**。

- **功能/端到端测试**：是否有 BDD 框架（如 Cucumber/Behave/SpecFlow 等）或其他 E2E 方案；`.feature` 文件放在哪里；步骤定义放在哪里
- **集成/接口测试**：使用什么框架与断言方式；如何隔离外部依赖（Mock/内存实现/容器）
- **单元测试**：测试框架、Mock 库、断言库

### 4.2 测试目录与命名约定

- 各层测试代码的目录位置
- 测试类/测试方法/测试文件的命名约定
- 测试标识的标注方式（如何把测试关联到 bug 触发条件——标签、注解、注释等既有做法）
- 运行测试的命令（从构建配置或脚本中提取）

若某子项目无任何测试先例，标注「{子项目名}无测试先例」，并给出与技术栈匹配的建议测试方案供用户确认。

**自我检查：**

- [ ] 三层测试各自的框架已识别（或标注无先例）
- [ ] **每个子项目**（前端/后端/其他模块）的测试框架已独立探测
- [ ] 测试目录与命名约定有证据
- [ ] 测试标识标注方式已明确
- [ ] 测试运行命令已提取（每个子项目）

## 步骤 5：范式 Profile 识别与选定

综合步骤 1（技术栈）与步骤 4（测试框架）的探测，对照 `.claude/commands/tdd_bug/` 下各 profile 的"适用判定"章节匹配信号，选定对应 profile；判定须指向证据文件。选定后进入该 profile 的形态章节（bug 流程加载"测试分层形态""审查探测方式""覆盖率工具落地"三章，不加载"契约产出形态"），在其选项集内按本项目真实探测挑定各处采用的具体形态（profile 给"选项与默认"，本步骤挑"实际用哪个"）。多形态并存是常态，按各层分别选定。

记录：

```
范式 profile：{android / web}（证据：{构建配置/测试依赖}）
测试分层形态：功能层 {...} / 集成层 {...} / 单元层 {...}（证据：{既有测试}）
审查探测方式：{测试标识标注符号}（证据：{...}）
覆盖率工具落地：{工具 / 无工具}（证据：{构建配置}）
```

无对应 profile、或某处形态在选项集内无匹配时，标注「无先例」给建议形态，纳入"待确认事项"供用户确认，确认后记入架构基线。

**自我检查：**

- [ ] 已选定范式 profile，判定有证据文件佐证
- [ ] 三处形态均在选项集内挑定，或标注无先例待确认
- [ ] 多形态并存情形已按各层分别选定

## 步骤 6：同类实现参考

在项目中查找与本次 bug 修复相似的既有代码（相似的模块、相似的业务动作、相似的数据流），作为修复的直接模仿对象。

- 定位 1~3 个最相近的既有功能实现
- 记录其从接口到持久化的完整文件清单（各层代表文件路径）
- 归纳其可复用的模式（分层调用方式、错误处理、测试写法）

若无同类实现，标注「无同类先例」。

**自我检查：**

- [ ] 已定位同类实现（或标注无先例）
- [ ] 参考实现的分层文件清单完整
- [ ] 可复用模式已归纳

## 步骤 7：本次改动落点

只读定位本次要**修改**的既有代码与既有测试，供下游测试用例开发与代码修改直接使用。bug 修复恒为改动型（修改既有代码行为），无需模式判定。

### 7.1 既有代码改动清单

基于「问题理解结果包·根因假设」+「复现结果包·触发路径与证据」，逐条定位受影响的既有源文件：

```
| 既有源文件路径 | 涉及的类/方法 | 改动性质 | 依据 |
|--------------|-------------|---------|------|
| src/.../XxxService.ext | XxxService.doYyy() | 修改方法体 | 根因假设 H1 |
| src/.../ZzzHandler.ext | ZzzHandler.old() | 移除逻辑 | 触发路径 |
```

### 7.2 既有测试改动清单

基于「问题理解结果包·回归范围圈定」，定位关联既有测试文件，区分处理方式：

```
| 既有测试文件路径 | 测试标识 | 处理方式 |
|---------------|---------|---------|
| test/.../XxxServiceTest.ext | AC-18 | 回归，不修改 |
| test/.../ZzzHandlerTest.ext | REG-01 | 受 bug 影响需转绿 |
| test/.../LegacyTest.ext | — | 作废 |
```

### 7.3 关联模块测试现状勘察

改动落点定位后，对本次改动**波及的模块/流程**做只读测试现状勘察，识别原有测试是否充足。勘察对象：本次改动涉及文件所属模块、以及调用/被调用该改动代码的相关模块。

**勘察内容**：

1. **模块原有功能测试覆盖**：该模块既有功能是否有对应的功能/集成测试？是否存在长期无测试的关键流程？
2. **集成测试链路完整性**：改动代码涉及的模块间调用链路，是否已有集成测试覆盖端到端贯通？
3. **缺口识别**：对照模块职责，列出"应有但缺失"的测试点（如某关键分支无断言、某异常路径无验证）。

```
| 模块/流程 | 既有测试现状 | 识别到的测试缺口 | 缺口严重度 | 建议补写用例 |
|----------|------------|----------------|-----------|------------|
| XxxService 模块 | 仅有 2 个单元测试，无集成测试 | 缺失对外接口的集成测试 | 高 | 建议补 2 个集成用例 |
| YyyHandler 调用链 | 调用链无任何测试覆盖 | 调用链路 3 个分支未验证 | 中 | 建议补 3 个用例 |
```

**勘察原则**：

- 缺口识别聚焦"本次改动波及范围内、原有应测而未测"的用例，不要求补全项目所有历史欠债。
- 识别到的缺口与「问题理解结果包·关联模块测试缺口登记」**合并为同一份缺口表**（避免重复），作为测试用例开发阶段"防回归用例"的输入源。

**自我检查：**

- [ ] 既有源文件改动清单有真实文件路径佐证
- [ ] 既有测试改动清单区分了修改/作废/回归
- [ ] 已完成关联模块测试现状勘察，识别到的测试缺口已登记（无缺口时标注"无缺口"）
- [ ] 缺口已与问题理解的缺口登记合并，无重复

## 质量门禁

| 检查项 | 通过标准 |
|--------|---------|
| 技术栈 | 主语言、框架、数据访问方式均有证据文件 |
| 分层落点 | 本次 bug 修复各层的目标目录明确 |
| 命名约定 | 命名/错误处理/依赖注入均有现有代码佐证 |
| 测试基线 | 每个子项目的三层测试框架、目录、命名、运行命令均已独立探测并明确；无测试先例处已标注并给出建议 |
| 范式 profile | 已选定 profile 且有证据；三处形态（测试分层/审查探测/覆盖率）在选项集内挑定或标注无先例；无对应 profile/形态处已纳入待确认 |
| 同类参考 | 已定位同类实现或明确标注无先例 |
| 改动落点 | 已定位既有源文件与既有测试改动清单；已完成关联模块测试现状勘察并登记测试缺口；已与问题理解缺口合并 |
| 无臆断 | 所有结论可指向证据文件，无凭空推断 |

**最终判断信号**：拿着这份基线，测试和代码阶段能明确知道用什么技术栈、放到哪个目录、按什么命名和分层来写。能，则本阶段完成。

**流转前的用户确认（条件性）**：若"待确认事项"非空——存在"无先例"的建议选型，或多种既有模式无法自我裁定的分歧——必须先向用户展示这些待确认项并获得确认，再流转到下一阶段：测试用例开发。若"待确认事项"为空（全部结论有证据、无分歧），则自动流转，无需确认。
