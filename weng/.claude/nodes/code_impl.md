# 流程节点：功能代码实现

## 核心理念

**镜像现有**：新代码必须自然融入现有代码库的风格与模式，写任何代码前先理解，最好的新代码读起来就像旧代码一样自然。
**黄金法则**：发现问题立即修复。永远不在已知的错误代码上进行开发
**迭代哲学**：不要对需求意外的代码进行修改，所有的改动都是为了目标需求
**最小抽象**：只为**当下真实存在**的需求写代码。抽象由第二个真实用例触发，绝不由"未来可能"或"为了测试"触发

## 前置条件

### Git 状态检测

| 当前状态 | 操作 |
|:---|:---|
| 分支干净 | 开始任务 |
| 存在未提交变更 | **停止** - 让用户先处理 |

## 执行流程

### 1. 需求加载

读取加载需求共识与改动计划文件

### 2. 执行

逐步执行每个改动任务：
1. **实现** - 严格遵守项目规范编写代码
2. **立即验证** - 每个任务完成需要验证代码是否符合需求与计划
3. **跟踪进度** - 记录每个任务的完成情况，更新进度报告，标注任务为完成

**处理偏差**：
- 记录**什么**与计划出现偏差
- 记录**为什么**出现偏差
- 记录**如何**解决偏差
- 偏差信息在报告中记录

### 2.1 抽象克制自检（每写一个新类型/接口/抽象层前必答）

引入接口、抽象基类、Gateway/Provider/Wrapper 包装层、泛型参数、DI 框架前，**必须逐条通过**以下检查，任一不通过则不引入：

| 检查项 | 通过标准 | 反例 |
|:---|:---|:---|
| **规则三** | 相同逻辑已真实出现第 3 次才抽取；第 1、2 次直接写/允许复制 | 为每个类镜像一个 `IXxx` 接口 |
| **接口=多实现** | 引入接口时，当下必须有 ≥2 个真实生产实现，或有明确的运行时替换需求 | 6-7 个接口只有"1 生产实现 + 1 测试引用" |
| **删测试法** | 自问"若不写单测，这个接口还需要吗？"答"不需要"则删除，改用构造注入具体类 | 纯为 mock 而抽象的接口 |
| **框架必落地** | 引入的库/框架必须在**本次改动内**产生真实调用 | Koin 已引入却全程手写 `getInstance()` |

> 为可测试性服务时：优先"构造函数注入具体类"或"注入 Dispatcher/Provider 函数"，而非给每个类配镜像接口。

### 3. 验证

1. 静态分析：自动修复lint错误
2. 用例对照(不跑测试)：按照**验证矩阵全覆盖**的测试目标，查验用例、需求、代码实现保持一致。
3. 此阶段只做基础源码编译验证，不跑全量测试
