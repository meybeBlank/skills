流程节点：需求落地
描述: 将用户的自然语言需求转化为结构化的技术方案，同时针对技术方案识别改动影响评估、验收条件矩阵和改动计划


# 需求落地

通过对输入需求的分析和理解，结合项目实际代码实现，梳理需求的影响范围，识别需求的验收条件矩阵，给出需求的实施计划。随着一步一步推进，将过程中所有的矛盾与相关未定义的细节暴露出来，然后逐一清晰明确，任何无法决断的内容都需要与用户反复磋商，直到与用户对整个需求的理解在所有的细节上达成一致。

## 核心理念

**理解先行**：在改动任何代码之前，必须确保完全理解用户想要什么，与用户理解达成一致。错误理解用户需求的代价远远高于等待用户确认
**消除模糊**：在推进理解用户需求的过程中，发现的所有存在冲突、模糊、存在多重理解的地方，都需要与用户反复磋商。杜绝需求存在模糊地带

## 目标

根据输入需求获得：
- 基于实际项目的需求理解重述
- 需求实施对当前项目的影响范围
- 需求对应的验收条件矩阵
- 需求对应的实施计划

## 阶段一 需求理解与重述

根据用户的输入需求，理解用户需求
1. 需要识别的要素：
    - **什么**：用户想要做什么？
    - **为什么**：背后的原因与动机？
2. 用清晰、无歧义的语言重述用户需求。

**必须用户确认**:
- 需求表述存在歧义
- 实现方式存在模糊地带
- 用户未考虑到的方面

**代码库探索**
| 类别 | 探索内容 | 目的 |
|:---|:---|:---|
| 1. 类似实现 | 与需求共识相似的现有功能 | 寻找类似开发模式、断点、组件、调用方式等 |
| 2. 命名约定 | 文件、函数、变量、常量、类、类导入 | 保持一致性 |
| 3. 错误处理 | 错误如何处理、传播、记录 | 统一错误处理机制 |
| 4. 日志模式 | 日志级别、格式、位置、记录 | 方便调试 |
| 5. 类型定义 | 类型、接口、开发模式与代码组织方式 | 类型安全 |
| 6. 数据库表 | 数据库表结构、关系、索引等 | 数据一致性和完整性 |
| 7. 测试模式 | 测试文件位置、命名、断言风格、测试框架等 | 理解测试策略与风格 |
| 8. 配置定义 | 配置文件、环境变量、数据库连接、特性开关等 | 理解项目配置方式 |
| 9. 依赖关系 | 依赖包、导入文件与库、内部模块关系 | 理解项目依赖关系 |

**代码库分析**
| 追踪 | 内容 |
|:---|:---|
| 1. 入口点 | 请求/动作如何进入系统，到达修改区域 |
| 2. 数据流 | 动作与数据如何通过相关代码路径方法流转 |
| 3. 关键类、方法的关联 | 如果改动关联的范围与影响 |
| 4. 状态记录与变更 | 系统状态如何记录，在哪里修改，影响什么 |
| 5. 关联契约与接口约定 | 数据流转必须遵守的API、接口、协议等 |
| 6. 模式 | 代码中使用的设计模式、架构模式等 |

**探索优先级**
| 优先级 | 内容 | 目的 |
|:---|:---|:---|
| P0 | 相关入口、动作与数据调用流转 | 理解调用链路 |
| P1 | 类似实现 | 保持一致性 |
| P2 | 类型、接口定义 | 类型安全 |

## 阶段四 验收条件矩阵

基于`需求理解共识`，穷举出所有`Given-When-Then`格式验收条件，覆盖正常路径和异常路径。

**穷举原则**
- **正常路径**：每个用户操作的所有成功分支
- **异常路径**：每个字段的校验失败、权限不足、资源不存在
- **边界条件**：空值、最大值、最小值、特殊字符、并发

**验证一致性**：基于最新信息，在穷举验收矩阵发现与`需求理解共识`、`代码相关范围分析`不一致的地方，必须解决冲突后再继续任务。

**必须用户确认**: 发现矛盾与冲突，并且无法自我裁定时，需要用户确认。

**结果**：

## 阶段五 制定需求实施计划

根据 `需求理解共识`、`代码相关范围分析`和`代码探索信息`，制定结构化的需求实施计划。

### 阶段流程

#### 1. 架构审查
- 确定成功标准
- 列出假设和约束条件
- 识别受影响的组件
- 检查类似实现，考虑可复用的模式

#### 2. 步骤拆解
创建详细的步骤，包含：
- 明确、具体的操作
- 文件路径和位置
- 步骤间的依赖关系
- 预估复杂度
- 潜在风险

#### 3. 实施顺序
- 按依赖关系排序
- 将相关变更分组
- 尽量减少上下文切换
- 支持增量式测试

### 需求实施计划模板
``` markdown
## 需求实施计划：[功能名称]

### 架构变更
- [变更 1：文件路径、描述、原因]
- [变更 2：文件路径、描述、原因]

### 实施步骤

#### 阶段 1：[阶段名称]
1. **[步骤名称]**（文件：path/to/file.ts）
   - 操作：具体要执行的操作
   - 原因：执行该步骤的理由
   - 依赖：无 / 需要步骤 X
   - 风险：低/中/高
   - 对应验收条件：[验收条件编号1]...

2. **[步骤名称]**（文件：path/to/file.ts）
   ...

#### 阶段 2：[阶段名称]
...

### 测试策略
- 单元测试：[验收条件编号1]...
- 集成测试：[验收条件编号2]...
- E2E端到端测试：[验收条件编号3]...

### 风险与缓解措施
- **风险**：[描述]
  - 缓解措施：[如何处理]

### 成功标准
- [ ] 标准 1
- [ ] 标准 2

### 最佳实践
1. 具体明确：使用精确的文件路径、函数名、变量名
2. 考虑边缘情况：思考错误场景、空值、空状态
3. 最小化变更：优先扩展现有代码而非重写
4. 保持模式一致：遵循现有项目约定
5. 支持测试：将变更结构设计为易于测试
6. 增量式思考：每个步骤都应可验证
7. 记录决策：解释"为什么"，而不仅仅是"做什么"
8. 测试矩阵全覆盖：确保所有验收条件都有对应的测试用例
```

### 规模划分

当功能较大时，将其拆分为可独立交付的阶段：

- **阶段 1**：最小可行 —— 提供价值的最小切片
- **阶段 2**：核心体验 —— 完成顺利路径
- **阶段 3**：边缘情况 —— 错误处理、边界情况、完善
- **阶段 4**：优化 —— 性能、监控、分析

每个阶段应可独立合并。避免需要所有阶段完成后才能正常工作的计划。

### 需检查的警示信号

- 大型函数（超过 50 行）
- 深度嵌套（超过 4 层）
- 重复代码
- 缺少错误处理
- 硬编码值
- 性能瓶颈
- 步骤没有明确文件路径
- 无法独立交付的阶段
- 测试矩阵未全覆盖，存在未测试的验收条件

**验证一致性**：基于最新信息，在制作实施计划时发现与`需求理解共识`、`代码相关范围分析`存在问题，必须解决问题后再继续任务。

**必须用户确认**: 发现矛盾与冲突，并且无法自我裁定时，需要用户确认。
