# BDD 自动化开发与流程管理引擎

**核心规则**：
1. **严格按照节点跳转规则执行**：必须按照每个节点定义的跳转规则跳转
2. **节点结果存档**：在项目的`trace_path`目录下对各个流程节点的最终产出内容进行存档，节点重复进入时，不更改已存在的产出内容，新建存档文件追加产出内容
3. **起始节点**：流程从 `需求理解` 节点开始，到 `代码提交` 节点结束
4. **用户手动确认**：需要用户确认的节点，必须让用户手动确认
5. **节点信息控制**：
  - **流程存档隔离**：节点在 `trace_path` 目录下只能读取其 **节点输入** 中明确列出的结果包文件，不得读取 `trace_path` 下其他节点的存档，避免上下文串味。
  - **项目源码不受限**：项目源码、配置、测试代码不属于流程存档，不受上述限制。
  - 简言之：受限的是 `trace_path` 内的跨节点存档；项目自身代码库不受限。
6. **审查隔离**：所有审查节点必须使用独立的子agent在隔离上下文中执行，禁止在主agent中直接审查。
7. **回退熔断**：任一"审查FAIL回退"或"测试失败回退"的循环，同一回退环连续回退达到 3 次仍未通过时，停止自动回退，向用户汇报卡点（失败原因、已尝试的修复、需用户决策的分歧），由用户决定继续、调整方案或终止。
  - **计数单位**：以"回退环"为单位独立计数，每个回退环互不干扰。
  - **计数存储**：计数在主流程上下文中跟踪，不落盘为文件。
  - **计数递增**：某回退环每发生一次"FAIL/失败 → 回到目标节点"即 +1。
  - **计数清零**：该回退环对应的审查节点判定 PASS后，此环计数清零；不同环的计数互不影响。
  - **熔断触发**：任一回退环计数达到 3 时停止该环的自动回退，上报用户。
8. **需求变更回退**：任何节点若发现需求本身需要调整（而非当前节点产出有误）——例如新暴露的场景、与用户确认后需求范围变化、下游发现上游需求存在根本性遗漏或矛盾——**必须先向用户确认**，确认后可回退到 `需求理解` 节点重新拆解。此类回退属于需求变更，**不计入任何回退环的熔断计数**。回退后从需求理解节点重新顺序流转，已有存档按存档规则新建追加，不覆盖。
9. **范式 Profile 驱动**：受项目结构影响的形态（契约产出形态、测试分层形态、审查探测方式、覆盖率工具落地）外置到 `.claude/profiles/<profile>.md`，按项目类型选定。
  - **选定时机**：`架构勘察`节点完成范式识别后选定 profile（如 `android` / `web`），写入架构基线结果包。profile 是形态的唯一裁定者，架构勘察是实例细节（框架版本、目录、命令、标注符号）的唯一裁定者，两者分工不重叠。
  - **加载节点**：`验证矩阵`、`API契约`、`测试用例`、`代码开发`、`代码重构`、`全量测试`及三个审查节点，除读取自身节点文件与所列节点输入外，**追加读取架构基线选定的 `.claude/profiles/<profile>.md` 的对应章节**执行。
  - **优先级**：节点文件为通用骨架规则，profile 为项目类型特化规则；同一事项两者冲突时 **profile 优先**。节点文件中出现的 OpenAPI/Cucumber 等具体形态一律视为"形态之一的示例"，实际形态以选定 profile 为准。
  - **兜底**：项目类型无对应 profile 时，架构勘察标注"无先例"，给出建议形态并经用户确认，确认结果记入架构基线，供后续节点沿用。

**覆盖率口径约定**（贯通全流程，三处覆盖率各司其职，不得混用）：
- **场景/规则覆盖率**（设计侧）：由`需求理解`、`验证矩阵`节点负责。衡量"业务规则与场景是否被测试计划覆盖"，门禁为规则覆盖率 100%、场景覆盖率 100%。回答"测试设计有没有漏场景"。
- **改动覆盖率**（实现侧）：由`代码开发`节点自检、`全量测试`节点复核。衡量"**本次改动涉及的文件、代码、模块**是否被测试充分覆盖"，门禁为改动涉及文件/模块行覆盖率 ≥ 80%、改动代码无未测分支。回答"本次改的东西有没有对应测试覆盖到位"。该口径**不要求全量行覆盖率达标**——全量历史遗留缺口不属于本次改动的放行阻碍，但需在结果包中显式标注为"既有遗留"，不得隐藏。
- **全量行覆盖率**（回归参考）：由`全量测试`节点统计，衡量"整体代码行/分支被测试执行的比例"。**仅作为回归趋势参考，不作为放行门禁**。结果包中如实记录全量数值，并对低于 80% 的缺口做归因（本次引入 vs 既有遗留），归因结论用于佐证改动覆盖率口径的判定。
- 三者关系：场景覆盖是源头（设计不漏），改动覆盖是门禁（本次改动覆盖到位），全量行覆盖是参考（回归趋势 + 缺口归因）。任一处报告覆盖率时必须标明是哪一类口径。

**改动型补充测试约定**（贯通改动型全流程）：改动型需求除按变更类型分批（修改/新增/废弃/回归）外，若在架构勘察或验证矩阵阶段发现**本次改动波及的模块/流程原有功能测试、集成测试存在缺口**（与本次需求无直接因果，但属于被改动代码所属模块应覆盖而历史未覆盖的用例），必须在本轮补写，纳入"补充"统一管理。补充用例须登记到验证矩阵追溯表、走标准红灯→转绿流程、纳入回归范围。**不得以"本次需求只改一个命名"为由跳过对所波及模块原有测试缺口的补救。**

**路径定义**:
- 文件存储路径：`trace_path` = `.weng/workflow/<时间戳-任务名>/`
- 节点存档文件名规则：`doc` = `trace_path/<节点执行序号>_<节点名>_<节点结果1>`
- 范式 profile 路径：`.claude/profiles/<profile>.md`（由`架构勘察`节点选定，供下游节点加载形态规则）

** 子agent编排 **：
- 子agent `bdd-stage-reviewer`（`.claude/agents/bdd-stage-reviewer.md`）：每次进入 `契约审查`、`测试审查`、`代码审查` 节点时，各创建一个新的审查agent，并以阶段参数区分审查内容（`contract` / `test-red` / `code-green`）。
- 子agent `code-refactorer`（`.claude/agents/code-refactorer.md`）：每次进入 `代码重构` 节点时创建一个新的重构agent，对当前 git diff 的实现代码做结构优化，不改行为、保持测试常绿。

节点存档示例：
``` 
假设有3个节点：节点1、节点2、节点3。节点3输出两个部分结果
一次任务的执行顺序为： 1 -> 2 -> 1 -> 3 (节点1进入两次，每次都会生成文档)
最终节点存档文件应该有5个：
- `trace_path/01_节点1`
- `trace_path/02_节点2`
- `trace_path/03_节点1`
- `trace_path/04_节点3_结果1`
- `trace_path/04_节点3_结果2`
```

## 节点：代码重构
** 流程编排规则文件 **：`.claude/nodes/bdd_refactor.md`
** 子agent **：`code-refactorer`（`.claude/agents/code-refactorer.md`），必须使用子agent在独立上下文中对当前 git diff 的实现代码执行结构优化，禁止在主agent中直接重构。
** 进入条件 **：上一节点（代码审查）结论为 PASS。审查 FAIL 时不会到达本节点。
** 节点输入 **：
  - `<doc>_代码开发结果包.md`（实现文件清单、绿灯确认）
  - `<doc>_代码审查报告.md`（其"建议项"是重构优先处理对象）
  - `<doc>_架构基线结果包.md`
  - `<doc>_契约.<ext>`（如果存在，重构须保持契约不变）
  - `<doc>_验证矩阵结果包.md`（回归范围，重构后须保绿）
  - 当前 git diff（本次绿阶段实现改动，重构对象）
** 节点结果 **：`<doc>_代码重构结果包.md`（重构清单、绿验证复核记录、未重构项、契约保持核对、待确认事项）
** 下一个节点 **：`全量测试`
  - 全绿且契约未变 → 跳转`全量测试`（重构的本质是"不改行为改结构"，全量测试是其最佳回归验证）
  - 存在回红且无法自修 → 跳转`代码开发`修复（计入代码重构回退环熔断计数，连续回退达 3 次触发熔断上报用户）
  - 触及契约 → 停止重构，上报用户决策是否回退`API契约`节点（属契约变更范畴，不计入回退熔断）

## 节点：全量测试
** 流程编排规则文件 **：`.claude/nodes/test_run.md`
** 节点输入 **：`<doc>_验证矩阵结果包.md`、`<doc>_架构基线结果包.md`（测试运行命令与覆盖率工具）
** 节点结果 **：全部通过/存在失败、覆盖率达标判定、`<doc>_测试结果汇总.md`
** 下一个节点 **：
  - 如果全部通过 **且** 改动覆盖率达标（本次改动涉及文件/模块行覆盖率 ≥ 80%、改动代码无未测分支；或项目无覆盖率工具经用户确认放行），跳转到`代码提交`节点
  - 存在失败用例 > 0 → 跳转到`代码开发`节点（连续失败回退达 3 次触发回退熔断，上报用户）
  - 测试全通过但改动覆盖率不达标 → 跳转到`代码开发`节点补充测试与实现（计入回退熔断），或经用户显式确认后放行到`代码提交`

** 流程编排规则文件 **：`.claude/nodes/commit.md`
** 节点输入 **：全流程各节点存档（trace_path 下结果包）、`<doc>_测试结果汇总.md`

** 下一个节点 **：任务完成。向用户进行汇报工作摘要
